# Мемоизация и ре-рендеры

Этот документ фиксирует политику мемоизации приложения: почему мемоизация здесь ручная, где её применять, а где сознательно не применять, и какие инварианты держать при будущих изменениях.

## React Compiler не подключён (сознательно)

Проект на React 19, но [React Compiler](https://react.dev/learn/react-compiler) намеренно **не** подключён (в сборке нет `babel-plugin-react-compiler`, `vite.config.ts` использует обычный `@vitejs/plugin-react`). На момент решения компилятор сочли слишком сырым для продакшена. Практическое следствие: вся мемоизация ручная (`useMemo`, `useCallback`, `memo`), поэтому её нужно расставлять осознанно, а не полагаться на автоматику.

Если решение пересматривается и компилятор подключается, бо́льшую часть ручных `useMemo`/`useCallback` можно будет удалить, а разрывы цепочек ре-рендеров (см. ниже) он закроет сам — тогда обнови эту страницу.

## Базовые правила

- **Селекторы Zustand атомарные.** Каждый селектор берёт один примитив или стабильную ссылку (`useHistoryStore((s) => s.groups)`), а не собирает новый объект/массив. Селектор вида `(s) => ({ a: s.a, b: s.b })` возвращает новую ссылку на каждый вызов и ре-рендерит потребителя на любое изменение стора — это главный footgun Zustand. Когда потребителю нужно несколько полей сразу, используй `useShallow` (см. хуки совместимости в `src/stores/index.ts`) или несколько атомарных селекторов.
- **Значение контекста мемоизируется.** Провайдер, кладущий объект в `value`, оборачивает его в `useMemo` (пример — `AppThemeProvider`), иначе каждый потребитель контекста ре-рендерится на любой ре-рендер провайдера.
- **Мемоизируй по реальной стоимости, а не по привычке.** `useMemo`/`useCallback` оправданы, когда закрывают дорогой расчёт, широкое поддерево или разрывают цепочку ре-рендеров через `memo`. Оборачивать примитив, дешёвое выражение или разовый inline-массив, который уходит в невроспринимающий его antd-компонент, не нужно — это только шум.

## `memo` окупается только со стабильными пропсами

`memo` на компоненте сравнивает пропсы поверхностно и пропускает ре-рендер, если они не изменились. Это работает лишь тогда, когда **все** пропсы стабильны между рендерами: примитивы, стабильные ссылки на данные из стора и колбэки, обёрнутые в `useCallback`. Один inline-колбэк (`onClick={() => ...}`), пересоздаваемый на каждом рендере родителя, сводит `memo` на нет.

### Список истории: `HistoryRecordsList` + `HistoryRecordRow`

Показательный случай — список записей истории. `HistoryPage` ре-рендерится часто (много подписок на стор, локальное состояние выбора/обработки). Раньше `HistoryRecordsList` пересобирал разметку всех строк дня на каждый такой ре-рендер, а выбор одной записи (`selectedRecordId`) перерисовывал весь список, включая regex-подсветку `HighlightedText` в каждой строке. Для активного пользователя диктовки день — это десятки строк, и клик по записи заметно подлагивал.

Решение (без React Compiler — вручную):

- Каждая строка вынесена в отдельный компонент `HistoryRecordRow`, обёрнутый в `memo`. Смена `selectedRecordId`/`processingRecordId` теперь перерисовывает только затронутые строки: у остальных пропсы не изменились.
- Сам `HistoryRecordsList` тоже обёрнут в `memo`, чтобы ре-рендеры `HistoryPage` по несвязанным причинам (например, ввод в поиске) не доходили до списка.
- Чтобы оба `memo` реально срабатывали, **колбэки, передаваемые из `HistoryPage` в список (`onRecordSelect`, `onCopyRecordText`, `onDeleteRecord`, `onRepeatTranscription`, `onActiveDatesChange`), обёрнуты в `useCallback`.** Это связанный инвариант: если снова передать их inline-стрелками, мемоизация строк и списка молча перестанет работать, а деградация производительности проявится только на больших днях. Признак выбранной строки и флаг обработки прокидываются в строку как примитивы (`isActive`, `isProcessing`), а не как ссылки.

## Что сознательно не мемоизировано

Не всякий частый ре-рендер стоит мемоизировать — если поддерево дёшево, `memo` только добавляет накладные расходы на сравнение пропсов.

- **Оверлеи записи** (`RecordingOverlay` → `CenterOverlay`/`BottomOverlay`) ре-рендерятся примерно на каждый кадр по событию `mic-level`, но рисуют крошечный DOM, а проп `levels` меняется каждый раз — `memo` на дочерних оверлеях не пропустил бы ни одного ре-рендера. Мемоизация здесь бесполезна.
- **Аудиоплеер истории** (`AudioPlayer`) обновляет `currentTime` по событию `timeupdate` (~4 раза в секунду), поддерево маленькое. Отдельная мемоизация не нужна.

## Как проверять эмпирически

Реальную стоимость и число ре-рендеров смотри через React DevTools Profiler — он доступен прямо в приложении в dev-режиме (см. раздел «React DevTools» в [index.md](index.md)). Не добавляй ручную мемоизацию «на всякий случай»: сначала подтверди, что ре-рендер дорогой и происходит часто.
