# Отладочное логирование

Отладочные логи предназначены для локальной диагностики вызовов моделей Speech-to-Text, постобработки и локального определения речи перед распознаванием, а также жизненного цикла встроенного плеера.

## Формат

Логи используют файлы `.log` только на дозапись, а не единый корректный JSON-документ.

Каждое событие записывается так:

```text
================================================================================
2026-06-21T18:42:12.123Z speechToText.response operationId=... historyRecordId=...
--------------------------------------------------------------------------------
{
  "timestamp": "...",
  "event": "speechToText.response"
}
```

Файл целиком не является корректным JSON. Полезная нагрузка каждого события — это JSON с отступами (pretty-printed), что делает длинные объекты запроса и ответа читаемыми, не требуя от приложения перечитывать и переписывать растущий файл при каждом событии.

## Файлы сессии

Текущая сессия логирования пишет в один файл отладочного лога. Новый файл создаётся лениво при первом залогированном событии после включения логирования.

Выключение логирования закрывает текущую сессию логирования. Повторное включение в рамках того же процесса создаёт новый файл при первой следующей записи логирования. Перезапуск приложения также начинает новую сессию логирования.

## Секреты

Отладочные логи не должны включать API-ключи, `Authorization`, байты аудио или значения пользовательских заголовков.

Пользовательские заголовки запроса могут логироваться по имени с булевым значением, указывающим, было ли значение задано. Это сохраняет возможность отлаживать конфигурацию провайдера, не храня секретные значения.

## Локальное определение речи

При включённом расширенном отладочном логировании каждый запуск удаления тишины начинается с события `vad.started`. Штатный итог записывается как `vad.completed`, а внутренний сбой — как `vad.failed`. Эти события содержат только безопасные метаданные: длительность до и после обработки, частоту дискретизации, число каналов, число сэмплов и сегментов, а также классификацию результата. Байты аудио, транскрипты, пути к библиотекам и исходные сообщения ошибок внешних библиотек не записываются.

Внутренние ошибки VAD дополнительно записываются как `vad.failed` даже при выключенном расширенном отладочном логировании. Классификация позволяет различить сбой ресемплинга, недоступную ONNX Runtime, отсутствие ресурса ONNX-модели, ошибку загрузки модели и ошибку инференса. Обычные результаты `noSpeech` и `speechTooShort` не являются внутренними сбоями и записываются только при включённом расширенном отладочном логировании.

## Сопоставление с историей

Диктовка создаёт ID записи истории до начала вызовов модели. События модели включают этот ID и исходную метку времени записи, поэтому запись лога можно сопоставить с финальной записью истории даже тогда, когда ошибка происходит до сохранения записи.

## Жизненный цикл плеера

Технические события `player.lifecycle` пишутся локально независимо от расширенного логирования. Они различают команды воспроизведения, паузы и перемотки, загрузку, фактический запуск и окончание источника, создание, смену состояния и закрытие контекста, скрытие окна, очистку и сбой. Backend дополнительно пишет `player.windowHidden` из общего пути скрытия главного окна: это позволяет проверить доставку уведомления frontend даже там, где GTK не сообщает DOM о скрытии.

Разрешённые метаданные — перечислимые тип и причина события, порядковые номера экземпляра плеера и запроса внутри текущего процесса, позиция и длительность в миллисекундах, состояние контекста, частота дискретизации и базовая задержка выхода. Граница IPC отвергает неизвестные поля, произвольные строки, отрицательные и выходящие за допустимые пределы значения. События не содержат аудио, транскрипций, путей, ID записей или исходных сообщений ошибок. Ошибки записи журнала не влияют на плеер. Покадровая синхронизация позиции не журналируется. Применяется общее удаление журналов старше 30 дней и ограничение суммарного объёма в 100 МБ.

Плеер закрывает `AudioContext` немедленно на паузе, скрытии и размонтировании, а при естественном окончании даёт выходу последних сэмплов ограниченный запас в 250–2000 мс по заявленной задержке устройства и затем закрывает контекст, сохраняя декодированный буфер только для выбранной записи. Новый контекст ждёт успешного закрытия предыдущего, в том числе между сменами записи. `resume` не входит в этот барьер, чтобы его зависание не мешало немедленному `close`. После отказа закрытия создание новых контекстов блокируется до перезапуска приложения, предотвращая накопление живых pipeline. Токены запросов запрещают запуск устаревшего источника после асинхронной загрузки, декодирования, проверки нативной видимости и `resume`. Потеря фокуса сама по себе не останавливает плеер. Эти меры устраняют удержание старого аудиопотока; они не доказывают первопричину любого самопроизвольного звука в системном аудиотракте.
