Ты готовишь и публикуешь релиз Transcriber. Релиз запускается пушем git-тега `v*`; CI сам синхронизирует версию в манифестах из тега и собирает сборку. Значение аргумента команды (может быть пустым): `$ARGUMENTS`.

## Незыблемые правила

- Никогда не выдумывай номер версии сам. Если пользователь не указал версию явно (ни в аргументе, ни в переписке), предложи вариант на основе существующих тегов и **дождись явного одобрения**, прежде чем что-либо делать.
- Работай только из ветки `main`, синхронизированной с `origin`. Сначала выполни `git fetch --tags origin` и убедись, что локальная `main` не отстаёт.
- Определи канал по формату версии: версия с дефисом (`-alpha`, `-beta`, `-rc`) — **нестабильный** релиз (канал unstable, canary-сборка); без дефиса — **стабильный** (каналы stable и unstable).
- После того как пользователь одобрил версию, ты сам делаешь коммит (для стабильного релиза), тег и пуш — отдельного подтверждения на пуш больше не спрашивай, но перед пушем покажи, что именно будет запушено.
- Тег ставь аннотированный: `git tag -a <tag> -m <tag>`.

## Предложение версии

Если версия не задана, посмотри теги и предложи следующий номер:

```bash
git tag --sort=-v:refname | head -20
```

Опирайся на semver и на объём изменений с последнего релиза. Предложи конкретный `vX.Y.Z` (или пре-релизный `vX.Y.Z-alpha.N`) и спроси одобрение. Не продолжай без ответа.

## Нестабильный релиз (версия с дефисом)

1. Убедись, что тег согласован с пользователем.
2. CHANGELOG не трогай — заметки для пре-релиза остаются пустыми, это ожидаемо.
3. Проверь чистоту рабочего дерева (`git status --porcelain`). Если есть незакоммиченные изменения, не относящиеся к релизу, — остановись и уточни у пользователя.
4. Поставь тег на текущий `HEAD` ветки `main` и запушь его:

   ```bash
   git tag -a <tag> -m <tag>
   git push origin <tag>
   ```

5. Сообщи, что workflow `Release` запущен: сначала job `check` (полный `npm run check`), затем сборка canary и публикация в канал unstable. Дай ссылку на вкладку Actions для наблюдения.

## Стабильный релиз (версия без дефиса)

1. Найди последний **стабильный** тег (без дефиса):

   ```bash
   git tag --sort=-v:refname | grep -vE '-' | head -1
   ```

2. Собери коммиты с этого тега:

   ```bash
   git log <lastStable>..HEAD --pretty=format:'- %s (%h)'
   ```

3. Составь заметки для CHANGELOG **на английском** (файл ведётся на английском), сгруппированные по Keep a Changelog (`Added`, `Changed`, `Fixed`, `Removed` и т. д.). Пиши по-человечески, с точки зрения пользователя, а не копируй сообщения коммитов дословно. Служебные коммиты (рефакторинг, тесты, CI) в заметки не включай, если они не меняют видимое поведение.
4. Предложи пользователю номер версии на основе объёма изменений и получи явное одобрение.
5. Обнови `CHANGELOG.md`: оставь пустой раздел `## [Unreleased]` сверху и вставь под ним новый `## [X.Y.Z] - YYYY-MM-DD` (сегодняшняя дата) с составленными разделами. Формат заголовка обязан быть ровно таким — по нему CI извлекает тело релиза (`scripts/extract-changelog.mjs`).
6. Закоммить только `CHANGELOG.md`:

   ```bash
   git add CHANGELOG.md
   git commit -m "docs(changelog): release vX.Y.Z"
   ```

7. Поставь тег на этот коммит и запушь коммит и тег:

   ```bash
   git tag -a vX.Y.Z -m vX.Y.Z
   git push origin HEAD
   git push origin vX.Y.Z
   ```

8. Сообщи, что workflow `Release` запущен: сначала job `check`, затем сборка и публикация. Релиз создаётся черновиком и публикуется автоматически после успешных проверок и загрузок. Дай ссылку на Actions.

## Если проверки в CI упадут

Job `check` гейтит сборку: при падении артефакты не публикуются, релиз остаётся черновиком. Тег при этом уже создан — сообщи об этом пользователю; после исправления можно перезапустить workflow вручную (`workflow_dispatch` с тем же тегом) либо пересоздать тег.
